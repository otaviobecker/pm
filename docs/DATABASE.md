# Database approach

The logical schema is in `docs/database-schema.json`. It is implemented with Python's standard `sqlite3` module; ten tables and a single local process do not justify an ORM.

## Storage and lifecycle

- The database path is `${DATA_DIR}/pm.db`, which resolves to `/app/data/pm.db` in Docker.
- Docker Compose mounts the named `app-data` volume at `/app/data`, so data survives container replacement and restart.
- Startup creates the directory and database when they do not exist.
- Startup reads `PRAGMA user_version` and applies numbered migrations in order, each in its own transaction. An empty file is created directly at the current version rather than replaying history. Each migration builds the schema of the version it upgrades *to*, never today's schema, so replaying history stays correct as the schema grows.
- Migrations rebuild tables, so they run on a connection with foreign keys disabled. The pragma is a no-op inside a transaction and is therefore set before `BEGIN IMMEDIATE`.
- Every other connection enables foreign keys, a 5-second busy timeout, and WAL journal mode.
- Tests override the path with a temporary database and never use the Docker volume.

## Model

- `users` holds one row per account: a case-insensitively unique username, a display name, an optional email, a PBKDF2 password digest, an `admin` or `member` role, and an active flag.
- `sessions` persists sign-in server side. Only the SHA-256 digest of the cookie value is stored, sessions expire after seven days, and they are extended when more than half their life has passed. Changing a password or deactivating an account deletes every session for that user.
- `boards` has one row per board, owned by a user. An account may own any number of boards, and a board can be archived instead of deleted.
- `board_members` decides who can open a board. `owner` may delete, archive, and manage members; `editor` may change the board's contents; `viewer` is read-only. Non-members receive a 404 rather than a 403, so board existence is not observable to outsiders.
- `columns` are ordered per board. New boards are seeded with `backlog`, `discovery`, `progress`, `review`, and `done`, and columns can then be added, renamed, reordered, and deleted. A board keeps at least one column, and a column with cards can only be deleted by naming where its cards go. An optional `wip_limit` caps how many cards a column accepts.
- `cards` use zero-based positions within a column. A composite foreign key ensures a card cannot point to another board's column. Each card carries a priority, an optional due date, and an optional assignee that must be a member of the same board.
- `labels` belong to a board, are limited to the product's five colors, and are attached to cards through `card_labels`. Deleting a label detaches it from every card.
- `card_comments` hold the discussion on a card. Any board member may comment, including viewers; the author may edit their own comment, and the author or the board owner may delete it. A deleted account leaves its comments in place with a null author.
- `checklist_items` are an ordered list per card. The board projection rolls comment and checklist counts up onto each card so the board can show progress without a second request.
- IDs exposed to the frontend stay stable: column IDs are strings unique within their board, card IDs are globally unique strings generated by the backend, and user and board IDs are integers.
- Timestamps are UTC ISO 8601 strings; due dates are plain `YYYY-MM-DD`.

## Transactions and ordering

Create, delete, reorder, and cross-column card moves run in one transaction. The backend rewrites positions for every affected column and updates the board timestamp before committing. Position updates use a high temporary positive range before assigning final zero-based positions, avoiding intermediate uniqueness collisions in SQLite. Column reordering uses the same technique.

AI updates use the same transaction boundary. The complete proposed update is validated before any write begins; a failure rolls back the entire update. An update may not add or remove columns, claim a card ID owned by another board, or reference the same card twice. Cards are reconciled in place -- removed, updated, or inserted -- rather than deleted and rewritten, so the labels, comments, and checklist hanging off a surviving card are not lost.

## API mapping

A board read assembles the shape the frontend consumes:

- columns are ordered by `columns.position`;
- each column's `cardIds` are ordered by `cards.position`;
- card records are returned as an object keyed by card ID, each carrying its label IDs and its comment and checklist counts;
- the board's labels, the caller's own role, and the member list travel with it.

A card's expanded view is a separate read that adds its comments and checklist. Every mutation on that view returns both the refreshed card and the refreshed board, because a comment or a checklist tick changes what the board shows.

Every read and write derives access from the authenticated session and the caller's board membership. Clients never select an arbitrary user ID.

## Initialization

On an empty database the schema is created in one transaction. Seeding then ensures the bundled `user` administrator exists with the default password and, if that account has no boards yet, inserts a starter board with the five default columns, four default labels, and the demo cards. Later starts leave existing data alone, so board changes are never overwritten. Registering a new account creates its own starter board the same way.
