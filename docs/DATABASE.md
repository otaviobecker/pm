# Database approach

The proposed logical schema is in `docs/database-schema.json`. Part 6 will implement it with Python's standard `sqlite3` module. Four tables and a single local process do not justify an ORM.

## Storage and lifecycle

- The database path is `${DATA_DIR}/pm.db`, which resolves to `/app/data/pm.db` in Docker.
- Docker Compose mounts the named `app-data` volume at `/app/data`, so data survives container replacement and restart.
- Startup creates the directory and database when they do not exist.
- Startup reads `PRAGMA user_version` and applies numbered migrations in order inside transactions.
- Every connection enables foreign keys, a 5-second busy timeout, and WAL journal mode.
- Tests override the path with a temporary database and never use the Docker volume.

## Model

- `users` supports multiple data owners. MVP authentication remains the hardcoded `user` / `password`; passwords and chat messages are not stored.
- `boards.user_id` is unique, enforcing one board per user.
- Each board is seeded with `backlog`, `discovery`, `progress`, `review`, and `done` column keys at positions zero through four.
- Column key and position changes, creation, and deletion are not API operations. Only the title is mutable.
- Database checks restrict column keys and positions, while startup seeding and the API enforce the invariant that all five columns exist. SQLite cannot express exact child-row cardinality with a simple table constraint.
- Cards use zero-based positions within a column. A composite foreign key ensures a card cannot point to another board's column.
- IDs exposed to the frontend remain strings. Column IDs retain the existing `col-{key}` values within each board, while card IDs are generated by the backend.
- Timestamps are UTC ISO 8601 strings.

## Transactions and ordering

Create, delete, reorder, and cross-column card moves run in one transaction. The backend rewrites positions for every affected column and updates the board timestamp before committing. Position updates use a high temporary positive range before assigning final zero-based positions, avoiding intermediate uniqueness collisions in SQLite.

AI updates use the same transaction boundary. The complete proposed update is validated before any write begins; a failure rolls back the entire update.

## API mapping

The read API assembles the existing frontend shape:

- columns are ordered by `columns.position`;
- each column's `cardIds` are ordered by `cards.position`;
- card records are returned as an object keyed by card ID.

All reads and writes derive the board through the authenticated user. Clients never select an arbitrary user ID.

## Initialization

On an empty database, the first migration creates the tables and constraints. Seeding then inserts the MVP user, their board, the five fixed columns, and the current demo cards in one transaction. Subsequent starts use `INSERT ... ON CONFLICT DO NOTHING` semantics so existing board changes are never overwritten.
